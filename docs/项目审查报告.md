## 2. 方向一：工作流程评审

状态常量单一真源在 `utils/constants.py`，业务校验集中在 `services/`，Vue API 统一走 `blueprints/vue_api*.py`。

### 2.1 巡检流程（最完善的流程）

**状态机**（`constants.py:32-38`）：待执行→{执行中,已取消}；执行中→{待审核,已取消}；待审核→{执行中,已完成}；已完成/已取消→∅
**链路**：任务创建（看板快捷/API/Excel 批量/合同与客户频率自动生成）→ 指派 → 执行传报告（全套资料+必传校验 `inspection_service.py:319`）→ 提交审核 → 审核（AI 辅助）→ 定稿（自动生成 Word 报告 + 任务已完成）

缺陷：
1. **P0 已完成/已取消是死胡同**（`constants.py:36-37`）：误操作无法重开，只能新建；批量改状态同受限，无 bypass 入口
2. **P1 无记录任务可直接"已完成"、有记录任务必须走审核**（`task_schedule_service.py:246-251`）：两条路径并存，"已完成"语义不一致
3. **P1 待审核无超时升级**：审核人长期不审则任务永久卡住，仅提交时有通知（`vue_api.py:2263`）
4. **P0 报告生成失败被静默吞掉**（`inspection_service.py:520-525`）：审核"已通过"但 report_file 为空，完整性检查持续报"缺失正式报告"，无修复入口
5. **P1 删除保护不一致**：任务页强制无记录才能删（`vue_api.py:1226`），记录页可自由删除并把任务拉回执行中
6. **P1 未指派任务上传校验短路**（`inspection_service.py:230-232`）：`assigned_to_user_id and current_user_id` 在未指派时短路放行，任意登录用户可给未指派任务传报告

### 2.2 工单流程

**状态机**（`ticket_service.py:14-22`）：待派单→{已派单,已关闭}；已派单→{处理中,已接单,待派单,已关闭}；已接单→{处理中,已派单,已关闭}；处理中→{待审核,已关闭}；待审核→{已验收,处理中}；已验收→{已关闭,处理中}；已关闭→∅
**链路**：创建（支持 self_accept 一键派单+接单）→ 统一动作 `/api/tickets/<id>/action` → 归档知识库案例

缺陷：
1. **P0 `ticket:review` 权限码定义却无人使用**：审核动作挂 `ticket:edit`（`vue_api.py:1530`），工程师可审核自己的工单
2. **P0 任意状态可无校验直接关闭**（`close_ticket` `ticket_service.py:225`）：不检查资料完整度，绕过诊断/方案/报告/审核全链路
3. **P0 已关闭无重开出口**：误关只能新建
4. **P1 已接单是不可达死状态**：accept_ticket 直接转"处理中"，转换表仅作历史兼容，但前端 dicts 下拉仍暴露"已接单"（`vue_api.py:1656`）
5. **P1 submit 无必填校验**（`ticket_service.py:145`）：诊断/方案/报告全可空，完整性只列表打标不强制
6. **P2 工单号取 max(id)+1**（`ticket_service.py:64-73`）：删除当日最后一张会重号撞唯一约束，并发无重试
7. **P2 无 SLA/时效监控**：priority 有值但无超时升级

### 2.3 故障流程（实质废弃，仅一次性脚本桥接）

- 故障 CRUD 仍在（`vue_api_ops.py:319-420`），模型注释"旧，逐步被 Ticket 取代"（`models/ticket.py:88`）
- 转工单是**一次性迁移脚本** `scripts/faults_to_tickets.py`，**前端无"转工单"按钮**，新故障进不了工单流
- 故障无状态机，处理结果为自由字段

### 2.4 备件流程

**链路**：采购入库（自动并/建库存行+流水 `_record_movement`）→ 销售出库（行锁防超扣 + FIFO + 低库存预警）→ 盘点调账 → 冲销回补

缺陷：
1. **P1 无借用/归还流程**：全库零命中，ITSM 场景（借备件临时替换）是明确缺口
2. **P1 多库位错位**：一个备件可建多行库存，但入库/冲销只操作**第一条库存行**（`spare_service.py:130/191`），与实际库位不符
3. **P2 无审批流**：采购/销售直接生效，靠权限兜底
4. **P2 出库与工单无关联**：无法追溯某工单消耗的备件
5. **P2 SQLite 行锁是 no-op**（`spare_service.py:153` 注释自述）——PG 化后需验证 `with_for_update` 生效

### 2.5 销售流程（商机→报价→合同→任务生成）

缺陷：
1. **P0 合同删除无关联保护**（`sales_service.py:202`）：可删除已生成任务的合同，`InspectionTask.contract_id` 外键无级联 → 悬挂引用（SQLite 默认不强制 FK 会脏数据，PG 强制 FK 会直接报错）
2. **P1 商机/报价/合同无状态转换表**：合同可从"已终止"直接改回"执行中"；商机阶段可跳级（初步接触→成交一步到位）
3. **P1 商机→合同无自动闭环**：成交/报价接受不自动生成合同，靠手工填 opportunity_id
4. **P2 任务标题客户名解析正则**（`task_schedule_service.py:29`）：只匹配 `yyyy年` 阿拉伯年份，"鄱阳湖水文2026年六月巡检"无法提取客户名
5. **P2 客户频率生成器跨年断层**：只生成本年度

### 2.6 客户 / 知识库 / 报告 / 机柜

- **客户**：两级树 + 自动任务 + 删除保护较完善；但**真删**（`customer_service.py:250` 注释建议软删除），历史统计会丢 → P1
- **知识库**：无发布审核（is_published 默认 true）、无收藏/关联检索 → P2
- **报告删除漏清引用**：只清 `Inspection.report_file` 与 `Ticket.report_file`（`ops/reports.py:40-41`），**漏 `Fault.report_file` 和 `SubmissionVersion.report_file`** → P0（产生 404 孤儿）
- **机柜**：U 位校验完备；但 `RackInstall.device_id` 无唯一约束，同一设备可重复上架不同机柜 → P2

### 2.7 权限与数据隔离

- RBAC 较完善（60+ 权限码、用户级 grant/deny、scope 数据范围）
- **P1 `apply_scope_filter` 的 customer_id 分支为空**（`permission.py:276-278`），且列表端点大多未调用 → 部门隔离基本未落地
- **P2 权限码脱节**：`permission:edit` 用于巡检检查清单配置语义牵强
- **P2 通知仅站内**：无外发渠道；逾期提醒只通知工程师本人不抄送主管

## 4. 方向三：备份 / 导入导出 / 迁移评审

### 4.1 备份脚本
| 脚本 | 结论 |
|---|---|
| `backup.sh` | PG 分支完整可用（pg_dump -Fc + meta tar + 保留 30 份）；SQLite 分支路径硬编码 `instance/itsm.db` |
| `update.sh` | **PG 模式此前无备份**（只复制死文件）→ 已修复：PG 调 backup.sh |
| `rollback.sh` | **原只支持 SQLite 文件恢复，PG 生产不可用** → 已修复：pg_restore + meta 还原 |
| `pg-migrate.sh` | SQLite→PG 9 步迁移，含密钥还原，较完整 |
| 定时备份 | **生产无 crontab** → 计划做 Web 配置（备份时间/保留数量） |

### 4.2 导出能力（较完善）
- **Excel**：设备/客户/巡检/工单/故障/备件 6 类（`blueprints/vue_export.py` 列配置 + `ExportDialog.vue`）
- **ZIP 资料包**：巡检 bundle、工单报告包（`utils/report_zip.py`）
- **加密 zip**：设备密码导出审核流（AES-256 pyzipper + 一次性口令头）
- **Word 报告**：巡检 9 章自动生成（`utils/report_generator.py`）
- **全量备份 zip**：`utils/data_io.py build_export_zip`（含密钥可选）
- **缺口**：库存/采购销售单/商机报价合同/任务安排/知识库/用户/拓扑等实体无列表导出

### 4.3 导入能力（不对称）
- **已有**：设备、客户、任务安排（Excel 批量，幂等 upsert）、巡检资产清单、系统全量备份导入（`perform_import` 覆盖恢复）
- **缺口**：备件/库存/巡检记录/故障记录**有模板下载无导入实现** → 计划补齐（服务层 + 预览/apply）

### 4.4 生产迁移（生产已是 PG，重点收敛）
- 切换仅需改 `ITSM_DATABASE_URI`，代码层 SQLite 特化极少（见方向四），曾用 pg-migrate 流程验证过
- **P0 雷点**：`views/system.py:24-38 repair_schema` 硬编码 SQLite 类型 `DATETIME` 补列，**PG 上 ALTER 会失败**（PG 无 DATETIME，应 TIMESTAMP）
- **P2 大导出内存压力**：备份导出 base64 全量回传浏览器（`vue_api_sys.py:639-646`），大数据量会顶不住 → 计划改 ExportFile token 直链
- **P2 无整机恢复脚本**：restore.sh 缺失，换机只能手工 → 计划补

## 5. 方向四：SQLite 与 SSR 剥离评审

### 5.1 SQLite 剥离（生产已是 PG，收紧运行时代码）
**好消息**：业务代码 SQLite 特化极少（`func.datetime/strftime/json_extract/last_insert_rowid` 零命中；JSON 字段全走 Python `json.loads`；日期逻辑在 Python 层；LIKE 用 ORM 方言方法）。需要处理的：
- `utils/data_io.py:422/492`：`PRAGMA foreign_keys=OFF/ON` 已按方言分支（PG 走 `SET CONSTRAINTS ALL DEFERRED`）→ 剥离 SQLite 分支
- `app.py:289`：遗留库引导的 `sqlite_sequence` 排除 → 剥离
- `utils/system_info.py`：`_sqlite3.sqlite_version` 分支 → 仅留 PG
- `views/system.py:66`：`DATETIME` 补列雷点 → 修复
- `tests/conftest.py:36`：**硬编码 SQLite URI**，全量测试跑 SQLite → 计划切 PG（读 `ITSM_TEST_DATABASE_URI`，`_fresh_db` 改 PG 兼容清库）；migrations 历史 SQLite 分支保留（存量兼容）

### 5.2 SSR 剥离（双轨 → 单轨）
**现状**：Vue 已全覆盖主业务（39 路由）；SSR 仅残留 5 个模板 + 若干纯 302 重定向视图。`utils/ui_version.py` 保留界面切换（默认 vue）。
- 仍存活的 SSR 页面：拓扑编辑器 `/topologies/editor/<id>`（**Vue 依赖**，window.open 调用，drawio iframe）、`/system/repair-schema`、`/system/drawio-diag`、4 个错误页、`/login`（POST 兼容 + 302）
- **Vue 不依赖 base.html**：CSRF cookie 由 `app.py:48-61` after_request 全局写；`request.ts` 复用同一机制（cookie 兜底）；base.html 的 fetch 包装仅作用于 SSR 页面
- **剥离清单**：templates/ 全部；views/ 纯渲染端点；blueprints 纯 302 重定向路由；`app.py` inject_sidebar/inject_csrf_token/from_json 过滤器 + 错误页 render_template；base.html 专属静态资源
- **保留**：`static/vendor/drawio` + `stencils`（拓扑编辑器依赖）、`fetch-drawio.sh`、after_request csrf cookie
- **依赖点**：conftest `login()` 用表单登录 `/login` → 剥离后需改 API 登录（影响全部测试，一次性机械改动）；拓扑编辑器需壳页化（去掉 Jinja 依赖）或迁 Vue 内嵌
