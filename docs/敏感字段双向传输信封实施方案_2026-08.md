# ITSM 敏感字段双向传输信封完整实施方案（2026-08）

> 状态：待实施
>
> 适用系统：ITSM Vue SPA + Flask JSON API
>
> 目标：在既有 HTTPS 和后端数据库 Fernet 加密之外，为设备密码等敏感字段增加浏览器与 Flask 应用之间的临时双向加密信封。
>
> 关联方案：`docs/工单故障处置时间与敏感凭据安全整合实施方案_2026-08.md`、`docs/内网TLS部署实施方案_2026-08.md`
>
> 明确边界：本方案不改变设备密码在数据库中的 Fernet 加密方式，也不使用 MFA 动态码、用户名或登录时间直接加密数据库记录。

## 1. 结论与总体设计

本方案采用“传输信封”和“数据库密文”两层独立机制：

```text
新增/修改：
浏览器明文
  → 临时 ECDH → HKDF → AES-256-GCM 请求信封
  → Flask 内存解密
  → 现有 Fernet 加密
  → 数据库密文

查看当前/历史密码：
数据库 Fernet 密文
  → Flask 内存解密
  → 临时 ECDH → HKDF → AES-256-GCM 响应信封
  → 浏览器组件内存解密和短时显示
```

核心决定如下：

1. 使用浏览器 Web Crypto 和后端 `cryptography` 的 P-256 ECDH、HKDF-SHA256、AES-256-GCM；当前项目已有 `cryptography==48.0.1`，后端无需新增密码学依赖。
2. 每个敏感操作使用一个 60 秒、单次消费的 challenge；同一 challenge 最多产生一条客户端到服务端消息和一条对应的服务端到客户端响应。
3. 用户 ID、用户名、`auth_version`、本次登录时间、MFA 成功时间、Session ID 摘要、challenge ID、HTTP 方法、API 路径、目标对象和传输方向进入服务端生成的上下文与 GCM AAD。
4. 上述账号和会话信息只用于绑定，不能作为对称密钥或 HKDF 输入密钥；真正的高熵输入密钥仅来自 ECDH 共享秘密。
5. MFA 动态码本身不发送给信封接口、不写入 AAD、不持久化、不参与数据库加密；信封只验证本次 Session 已完成 MFA。
6. 设备密码新增、修改、当前密码查看、历史密码查看首批接入；设备 Excel 密码导入、密码导出包解压口令随后接入；AI Key、通知渠道凭据等按统一 purpose 注册表扩展。
7. HTTPS 仍是正式安全边界。应用层信封可使反向代理到 Flask、HTTP body 日志和被动抓包中看不到业务明文，但不能防御被篡改的 SPA、浏览器扩展、XSS 或已入侵的应用进程。

## 3. 安全目标、威胁模型与非目标

### 3.1 要解决的问题

- 在浏览器开发者工具、代理访问日志、APM 请求体采集、反向代理到 Flask 的内部链路和被动抓包中，不出现设备密码等敏感字段明文。
- 已截获的信封不能跨用户、跨 Session、跨登录、跨接口、跨目标对象或跨方向使用。
- 同一信封不能重复消费；Gunicorn 多 worker 并发下也只能成功一次。
- 设备新增/修改与当前/历史密码查看采用同一协议，不出现“写入加密、查看又明文返回”的半闭环。
- 浏览器中的明文只存在于输入控件和短时展示组件内存，不进入 Pinia、localStorage、sessionStorage、URL、普通日志或错误上报。

### 3.2 能降低的风险

- HTTPS 在代理处终止后，代理到 Flask 若暂时为 HTTP，业务密码字段仍保持应用层密文。
- 误开启 request/response body 日志时，日志只能记录信封元数据和密文。
- 被动监听者无法解密，也不能篡改而不触发 GCM tag 校验失败。
- 截获的请求不能换设备 ID、历史记录 ID、HTTP 方法或路径后重放。

### 3.3 明确不能解决

- 通过普通 HTTP 下载的 SPA 可被主动中间人替换；攻击者能在加密前读取输入。因此标准浏览器必须从已有 HTTPS 域名加载 SPA，不能把本方案宣传成 HTTP 上的端到端安全。
- XSS、恶意浏览器扩展、终端木马、已入侵的 Flask 进程仍能接触使用时明文。
- 已授权用户查看、复制或拍摄密码后的泄露，不属于传输信封可解决范围。
- 数据库、备份和服务端静态密文安全仍由现有 Fernet 主密钥、密钥轮换和配对备份机制负责。
- 登录密码与本次 MFA 验证码发生在敏感会话建立之前，继续完全依赖 HTTPS；本方案不改写登录协议。

## 4. 密码学协议

### 4.1 算法套件

协议版本 `v1` 固定为：

| 项目 | 选择 | 约束 |
| --- | --- | --- |
| 密钥协商 | ECDH P-256 | 每个 challenge 前后端各生成一次临时密钥对，不复用 |
| 密钥派生 | HKDF-SHA256 | 32 字节随机 salt；c2s、s2c 使用不同 `info` |
| 对称加密 | AES-256-GCM | 每个方向独立 256-bit key、96-bit 随机 IV、128-bit tag |
| 上下文摘要 | SHA-256 | 对服务端规范化上下文求摘要 |
| Session 绑定 | HMAC-SHA256 | 服务端密钥计算摘要，不下发原始 session nonce |
| 编码 | Base64url 无填充 | JWK 的 x/y 按 Web Crypto 规范处理 |

依据：Web Crypto 标准定义了 `SubtleCrypto` 及 ECDH、HKDF、AES-GCM 能力；AES-GCM 是带附加认证数据的认证加密模式。参考 [W3C Web Cryptography API](https://www.w3.org/TR/webcrypto/)、[RFC 5869 HKDF](https://www.rfc-editor.org/rfc/rfc5869)、[NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)。

### 4.2 为什么不直接用 MFA、用户名和登录时间派生密钥

- 6 位 TOTP 有效搜索空间很小，不能承担离线抗穷举密钥职责。
- 用户名、用户 ID、登录时间、HTTP 路径均可预测或可观察，不增加密码学熵。
- Session ID 摘要用于证明同一会话上下文，不应被误当作共享秘密。
- 因此 ECDH 提供高熵共享秘密；MFA/账号/会话数据通过 AAD 绑定到密文，任何篡改或错配都会使 AES-GCM 验证失败。

### 4.3 权威上下文

服务端为每个 challenge 生成以下上下文；前端不能自行决定这些值：

```json
{
  "protocol": "itsm-credential-envelope",
  "version": 1,
  "challenge_id": "f4d2...",
  "purpose": "device.password.reveal",
  "direction": "c2s",
  "user_id": 12,
  "username": "zhangxinyue",
  "auth_version": 7,
  "auth_strength": "mfa_totp",
  "login_at": "2026-08-30T09:12:31.221Z",
  "mfa_verified_at": "2026-08-30T09:12:42.004Z",
  "session_binding": "hmac-sha256-base64url",
  "operation_binding": "sha256-of-validated-op-token-or-not-required",
  "method": "POST",
  "path": "/api/v2/devices/123/reveal-password",
  "target_type": "device",
  "target_id": "123",
  "history_id": "456",
  "issued_at": "2026-08-30T10:01:01.000Z",
  "expires_at": "2026-08-30T10:02:01.000Z"
}
```

约束：

1. `path` 使用不含 query string 的实际规范路径；路径参数同时写入 `target_id/history_id`。
2. `username` 是 challenge 签发时快照，`user_id` 和当前数据库账号必须一致。
3. `session_binding` 是 HMAC 摘要，不是 Flask cookie、Flask-Login `_id` 或原始 session nonce。
4. `operation_binding` 只绑定已经验证的短期操作令牌摘要；令牌原文不得入库或入日志。
5. c2s 和 s2c 分别生成 AAD。服务端返回 `request_aad`、`response_aad` 的 Base64url 编码，浏览器直接使用字节，不自行拼 JSON，避免前后端序列化差异。
6. 服务端消费时从 challenge 记录和当前 Session 重建并核对上下文，不能信任请求回传的 context。

### 4.4 双向密钥派生

双方计算 ECDH 共享秘密 `Z` 后：

```text
context_hash = SHA256(canonical_base_context)

K_c2s = HKDF-SHA256(
  ikm=Z,
  salt=challenge.salt,
  info="itsm-credential-envelope/v1/c2s/" || challenge_id || context_hash,
  length=32
)

K_s2c = HKDF-SHA256(
  ikm=Z,
  salt=challenge.salt,
  info="itsm-credential-envelope/v1/s2c/" || challenge_id || context_hash,
  length=32
)
```

禁止用同一派生 key 同时处理两个方向。每个 challenge 每个方向只允许一条消息，配合随机 96-bit IV 消除 nonce 重用风险。

## 5. 完整交互流程

### 5.1 MFA 登录和 Session 建立

1. 用户名、密码和 MFA 登录仍走现有 HTTPS 登录接口。
2. MFA 验证成功后，`establish_session()` 写入：
   - `auth_version`；
   - `login_at`（服务端 UTC 时间）；
   - `mfa_verified_at`；
   - `auth_strength=mfa_totp|mfa_recovery`；
   - 32 字节随机 `session_nonce`；
   - 现有 IP、UA 和活动时间。
3. 未经过 MFA 的 Session 可以使用普通非敏感功能，但不能申请任何凭据信封 challenge。
4. 登出、密码修改、MFA 重置、用户停用和 `auth_version` 变化立即使全部未使用 challenge 失效。
5. 权限和客户 scope 在 challenge 签发及业务端点消费时各检查一次，challenge 不能固化旧权限。

### 5.2 challenge 签发

新增接口：

```http
POST /api/security/credential-envelope/challenge
X-CSRFToken: ...
X-Operation-Token: ...   # purpose 要求操作验证时必填
Content-Type: application/json
```

请求：

```json
{
  "version": 1,
  "purpose": "device.password.reveal",
  "target_id": 123,
  "history_id": 456,
  "client_public_key": {
    "kty": "EC",
    "crv": "P-256",
    "x": "...",
    "y": "...",
    "ext": true
  }
}
```

后端必须通过 purpose 注册表推导 method/path/权限/操作验证要求，不接受客户端任意指定路由。签发响应：

```json
{
  "code": 0,
  "data": {
    "version": 1,
    "challenge_id": "f4d2...",
    "kid": "env-wrap-2026-01",
    "server_public_key": {
      "kty": "EC",
      "crv": "P-256",
      "x": "...",
      "y": "...",
      "ext": true
    },
    "salt": "base64url-32-bytes",
    "request_aad": "base64url",
    "response_aad": "base64url",
    "expires_at": "2026-08-30T10:02:01.000Z"
  },
  "message": ""
}
```

### 5.3 新增或修改设备密码（c2s）

前端保存设备时：

1. 从表单副本提取 `password` 并立即删除该字段；普通设备字段继续放外层 JSON。
2. 生成不可导出的临时 P-256 私钥；用公钥申请 `device.password.create` 或 `device.password.update` challenge。
3. 用 `K_c2s` 加密最小载荷：

```json
{
  "password": "用户输入值"
}
```

4. 业务请求结构：

```json
{
  "customer_id": 18,
  "device_name": "核心交换机",
  "other_normal_fields": "...",
  "credential_envelope": {
    "version": 1,
    "challenge_id": "f4d2...",
    "iv": "base64url",
    "ciphertext": "base64url-including-gcm-tag"
  }
}
```

5. 后端在权限、scope、Session、操作令牌和 challenge 校验全部通过后，在内存中解密；只把得到的 `password` 注入 service 表单。
6. `services/device_service.py` 继续调用现有 `encrypt_password()` 保存 Fernet 密文和密码历史。
7. `required` 模式下，请求只要出现外层 raw `password` 即返回 400 并写不含值的安全事件。
8. 无密码变更的普通设备编辑不申请 challenge，不改变现有交互性能。

### 5.4 查看当前或历史密码（c2s + s2c）

1. 浏览器申请 `device.password.reveal` challenge，purpose 中绑定设备 ID 和可选历史 ID。
2. 浏览器用 `K_c2s` 加密 `{ "history_id": 456 }` 作为持有临时私钥的证明。
3. 后端执行现有 `device:reveal` 权限、客户 scope、限流、操作令牌和审计检查，再消费 challenge。
4. 后端 Fernet 解密当前或历史记录后，立即用 `K_s2c` 加密：

```json
{
  "password": "服务端解密值",
  "kind": "history",
  "history_id": 456
}
```

5. 响应只包含信封：

```json
{
  "code": 0,
  "data": {
    "credential_envelope": {
      "version": 1,
      "challenge_id": "f4d2...",
      "iv": "base64url",
      "ciphertext": "base64url-including-gcm-tag"
    }
  },
  "message": ""
}
```

6. 前端工具函数在调用栈内解密，页面只接收返回的字符串；不得写回 `detail.value`、Pinia 或缓存。
7. 明文展示默认 60 秒自动关闭；Dialog 关闭、路由离开、登出和组件卸载立即清空 ref。复制动作保留现有审计。浏览器剪贴板无法可靠远程清除，UI 必须提示用户自行保护。
8. 响应增加 `Cache-Control: no-store, private`、`Pragma: no-cache`，不允许 Service Worker 或浏览器缓存敏感响应。

### 5.5 设备 Excel 密码导入

设备导入模板允许密码字段，因此不能只改 JSON 接口。第二批按以下方式接入：

1. 前端读取 Excel 为 `ArrayBuffer`，申请 `device.password.import` challenge，使用 `K_c2s` 加密整个文件，而不是只加密某一列。
2. 提交 multipart：`challenge_id`、`iv`、`encrypted_file`、普通导入模式参数；不再提交原始 `import_file`。
3. 当前上限 20 MB。WebCrypto 需在内存中处理完整文件，前端在加密前检查大小并显示明确进度；超过上限拒绝，不能降级明文。
4. 后端解密后优先用 `BytesIO` 交给 Excel 解析；确需临时文件时使用私有临时目录、0600 权限和 `finally` 删除，不写 `static/uploads`。
5. 预检与正式执行各使用新的 challenge；不得复用预检密文。正式执行继续使用 `batch_id + file_sha256` 幂等逻辑，SHA256 对解密后的原始文件计算。
6. 不含密码列的普通设备导入也建议统一走加密文件，避免前端自行解析表头形成两套路径；灰度期可保留 HTTPS 明文文件兼容，required 阶段全部收紧。

### 5.6 密码导出包解压口令

当前 ZIP 内容已用 AES-256 加密，问题是解压口令通过 `X-Export-Password` 明文下发。改为：

1. 保留申请、审批、一次性 token 和 AES ZIP 文件生成逻辑。
2. 新增 `POST /api/v2/devices/export-password-download/<token>/authorize`；客户端携带 `device.password.export_unlock` challenge 的 c2s 信封。
3. 服务端验证申请人、审批状态、下载状态和 challenge 后，返回：
   - s2c 加密的 ZIP 解压口令；
   - 60 秒的一次性 `download_ticket`；
   - 文件名。
4. 客户端用 `download_ticket` GET 二进制 ZIP；响应不再含 `X-Export-Password`。
5. 文件真正开始发送时才标记下载；授权但未下载的 ticket 到期可重新授权，避免网络故障永久丢失文件。
6. 备份包等共用 `serve_export_file()` 的解压口令同步迁移，不能只修设备密码表而遗留同类明文响应头。

## 6. purpose 注册表与扩展范围

新增服务端单一真源 `CREDENTIAL_ENVELOPE_PURPOSES`，禁止路由自由拼接安全规则：

| purpose | 方向 | 目标接口 | 权限 | 操作验证 | 首批 |
| --- | --- | --- | --- | --- | --- |
| `device.password.create` | c2s | `POST /api/devices` | `device:add` | 有密码时要求 | 是 |
| `device.password.update` | c2s | `PUT /api/devices/{id}` | `device:edit` | 要求 | 是 |
| `device.password.reveal` | c2s+s2c | `POST /api/v2/devices/{id}/reveal-password` | `device:reveal` | 要求 | 是 |
| `device.password.import` | c2s | `POST /api/v2/devices/import` | `device:add` | 要求 | 第二批 |
| `device.password.export_unlock` | c2s+s2c | 密码包授权 | 相应导出权限 | 要求 | 第二批 |

### 7.3 临时服务端私钥保护

多 worker 不能把服务端临时私钥只放进进程字典，否则 challenge 在不同 worker 消费会失败；也不能明文放数据库。采用独立环境密钥：

- `ITSM_ENVELOPE_WRAP_KEY`：Base64 编码的 32 字节随机值；仅用于 AES-256-GCM 包装 60 秒临时 ECDH 私钥。
- `ITSM_ENVELOPE_WRAP_KID`：当前包装密钥标识。
- 私钥包装 AAD 绑定 challenge ID、purpose 和 expiry。
- challenge 使用后立即将 `server_private_key_wrapped` 置空；拒绝/过期记录同样清空。
- 包装密钥丢失只影响尚未使用、最长 60 秒的 challenge，不影响设备数据库密文和历史备份。
- 轮换时短暂配置 current + previous 两把包装密钥，等待 `TTL + 30 秒` 后删除 previous；不需要重新加密数据库设备密码。

此密钥与项目根 `.secret.key`/Fernet 主密钥职责分离，禁止互相替代。

### 7.4 原子消费与多 worker

消费流程在 PostgreSQL 事务中完成：

1. `SELECT ... FOR UPDATE` 锁定 challenge。
2. 检查 `status=issued`、未过期、当前用户/Session/`auth_version`/MFA/操作令牌/权限/scope/路径均一致。
3. 解包服务端私钥，校验客户端 P-256 公钥，派生 c2s/s2c key。
4. 校验 GCM tag 并解密；任何失败统一返回“安全信封无效或已失效”，不暴露具体密码学失败点。
5. 写 `used_at/status/client_ciphertext_hash` 并清空临时私钥。
6. 对查看操作在同一请求内生成 s2c 响应；对写操作进入现有业务 service。

同一 challenge 并发请求只能一个拿到 `issued` 状态。客户端不得自动重放同一密文；网络失败或业务校验失败后重新申请 challenge。

### 7.5 生命周期清理

- 签发 TTL 默认 60 秒，可配置范围 30–120 秒。
- 每次签发/消费顺带把已过期行标记 expired 并清空私钥；另由定时任务每日删除 7 天前的元数据。
- 安全审计表保留 challenge ID 的截断摘要和结果即可，不保留公钥、salt、IV、密文和私钥。
- challenge 数量按用户/IP 限流；建议签发 `30/分钟/用户、60/分钟/IP`，查看业务端点继续沿用更严格限流。

## 8. 前端设计

### 8.1 公共工具

新增 `frontend/src/utils/credentialEnvelope.ts`：

- `isEnvelopeSupported()`：检查 HTTPS secure context 与 `crypto.subtle`；生产不支持时明确报错，禁止静默降级。
- `createEphemeralKeyPair()`：P-256，私钥 `extractable=false`，只导出公钥 JWK。
- `deriveDirectionalKeys()`：ECDH + HKDF，返回不可导出的 AES-GCM keys。
- `encryptRequest()`、`decryptResponse()`：只接受 `Uint8Array`/最小对象；内部完成 UTF-8、Base64url 和 GCM。
- `withCredentialEnvelope()`：申请 challenge、执行一次业务调用，在 `finally` 清理可达引用。
- 不把私钥、派生 key 或明文写入 Axios config、Pinia、控制台、错误对象和 telemetry breadcrumb。

新增 `frontend/src/api/security.ts` 只负责 challenge 契约；设备 API 暴露高层函数：

- `createDeviceWithCredential()`；
- `updateDeviceWithCredential()`；
- `revealDeviceCredential()`；
- `importDevicesEncrypted()`；
- `authorizePasswordExportDownload()`。

组件不得自行拼 AAD 或调用密码学原语。

### 8.2 内存与 UI 规则

- 表单密码字段使用独立 ref，不进入可序列化的通用设备对象；如果短期无法拆表单，保存前必须先提取并删除副本字段。
- 查看结果只进入敏感值 Dialog 的局部 ref，默认 60 秒倒计时。
- Dialog 关闭、页面跳转、浏览器标签隐藏超过阈值、登出和组件卸载均清理显示值。
- 不使用 `v-html` 显示敏感内容；不在 toast 中回显密码。
- 复制仍需用户主动点击，并调用现有 `password-copy-audit`；不承诺自动清空系统剪贴板。
- 网络面板会看到 `challenge_id/iv/ciphertext`，看不到 `password`、ZIP 解压口令或 AI Key。

### 8.3 浏览器兼容

- Web Crypto 的 `SubtleCrypto` 是 secure-context 能力。生产应从现有 HTTPS 域名访问；`http://172.16.123.124:5000` 不作为 required 模式的敏感操作入口。
- 目标浏览器为当前受支持的 Edge/Chrome；发布前用生产实际版本验证 P-256 ECDH、HKDF、AES-GCM 和 JWK 导入导出。
- 不支持 Web Crypto 的浏览器仍可查看普通列表，但保存/查看敏感字段时显示“请使用受支持浏览器并通过 HTTPS 域名访问”，不得回退明文。
- 不引入运行时 CDN 密码学脚本；所有 SPA 资源仍由当前构建产物发布并校验完整性。

建议新增：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `ITSM_CREDENTIAL_ENVELOPE_MODE` | `off` | `off/optional/required` |
| `ITSM_CREDENTIAL_ENVELOPE_PURPOSES` | 空 | 分 purpose 灰度，不支持任意字符串 |

模式语义：

- `off`：不签发 challenge；仅用于开发前和紧急代码回退。
- `optional`：新前端优先使用信封；旧 HTTPS 客户端暂时可走兼容路径，但必须统计 raw 敏感请求数量且不记录内容。
- `required`：选定 purpose 只接受信封；出现 raw 敏感字段直接拒绝。

生产回滚不能把 HTTP 明文兼容作为常态。若 required 紧急回退到 optional，只允许已有 HTTPS 域名，且需生成安全告警和限时恢复单。

## 10. 审计、日志与可观测性

### 10.1 允许记录

- challenge ID 截断摘要、purpose、目标对象、用户 ID/用户名、`auth_version`、认证强度、签发/消费结果、耗时、IP、UA。
- 失败分类只记录 `expired/reused/context_mismatch/invalid_envelope/permission_denied` 等枚举。
- 指标：签发数、成功率、过期率、重放拒绝数、raw 请求拒绝数、浏览器不支持数、解密失败数和 P95 耗时。

### 10.2 禁止记录

- MFA 动态码/恢复码、原始 operation token、session nonce/cookie。
- ECDH 私钥、共享秘密、HKDF key、AES key。
- 设备密码、AI Key、通知凭据、ZIP 解压口令。
- 完整 ciphertext、GCM tag、IV、salt、公钥 JWK 和原始 AAD。
- 解密后的请求体或响应体。

### 10.3 防止通用中间件泄漏

- `request.ts` 的调试/错误处理不得序列化解密结果。
- Flask 异常处理和 APM 对信封端点关闭 body capture；仅记录长度和摘要。
- 反向代理不记录请求/响应 body；即使误开也只能看到密文。
- 安全测试用唯一 canary 密码扫日志、审计表、响应、前端存储和构建产物，结果必须为零。

## 15. 回滚与故障处理

### 15.1 可逆边界

- 信封故障不改变现有 Fernet 数据，回滚前后数据库设备密码无需迁移或重加密。
- Alembic downgrade 只允许在确认无运行 challenge 后删除 challenge/ticket 表；保留空表通常更安全。
- wrap key 丢失只丢弃最多 60 秒的未使用 challenge，生成新 key 后重新申请即可。
- 前端发布失败按现有不可变资源回滚；后端 optional 模式仍可兼容上一版 HTTPS 客户端。

### 15.2 生产故障动作

1. 优先将出问题的单一 purpose 从 required 暂退到 optional，不整体关闭所有安全能力。
2. optional 回退只允许 HTTPS 域名，不恢复 HTTP raw 密码例外。
3. 清理未使用 challenge，检查 wrap key/KID、服务器时间、Session MFA上下文、权限和 CSRF。
4. 禁止通过记录明文请求体定位问题；使用 challenge 摘要、失败枚举和固定测试向量排查。
5. 恢复后重新观察 raw 请求归零，再切 required，并补安全事件说明。

- [ ] 确认生产外网/统一入口 HTTPS 域名及代理路由可覆盖所有 `/app/*`、`/api/*`。
- [ ] 盘点所有写入、查看和下载 secret 的接口，确认 purpose 表无遗漏。
- [ ] 明确 MFA recovery 登录是否允许直接申请 challenge；建议仍要求有效的操作验证。
- [ ] 确认用户停用、密码/MFA/用户名安全变更均递增 `auth_version` 或强制登出。

## 17. 最终安全边界说明

本方案实施后，MFA 用于确认本次登录身份，账号/登录/Session/接口信息用于防错用与防重放，ECDH/HKDF/AES-GCM 负责临时双向传输保密和完整性，Fernet 继续负责服务端数据库静态加密。四者职责清晰、相互不替代：

- MFA 不是加密密钥；
- 会话上下文不是数据库密钥；
- 传输信封不替代 HTTPS；
- Fernet 数据库密文不绑定某次登录；
- 查看密码和写入密码使用同一双向协议闭环。

按 E1 → E2 → E3 分批实施后，设备密码的新增、修改、当前查看、历史查看、批量导入和导出包解锁均可做到业务载荷不以明文出现在浏览器与 Flask 之间，同时保持现有数据库密文、备份和密钥轮换机制独立可恢复。
