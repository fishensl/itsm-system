# 通知拓展交付与运维说明

日期：2026-09-12。第二至四期已在本地实现，与第一期一并交付。未推送、未生产部署、未向真实机器人发送测试。

## 功能与入口

| 范围 | 已实现 |
|---|---|
| 客户通知设置 | 多群、企业微信/钉钉/飞书、独立启停、事件开关、加密凭据与加签、主动测试、解绑 |
| 可靠投递 | 同事务业务事件、PostgreSQL 独立消费者、唯一去重、并发领取、租约、有限重试、未知结果人工补发 |
| 通知中心 `/app/notification-center` | 状态数量、接口接受率、含排队平均耗时、客户/渠道分组、最早待发、心跳、分页投递与尝试记录、补发、模板版本发布、公开进展 |
| 工单及巡检展开详情 | 按业务对象展示受众、渠道、状态、原因和时间，权限仍按通知查询与客户范围执行 |
| 订阅与提醒 | 北京时间静默、进展合并、逾期/待审/退回提醒、主管及管理员升级、个人日报周报、客户服务摘要、失败站内告警 |
| 个人通知 `/app/notifications` | 当前用户消息、分类、未读筛选、已读及个人订阅 |
| 客户服务通知 `/app/customer-notifications` | 当前关联客户安全事件、登录后可选反馈、最多 500 字反馈、30 天确认有效期 |

客户联系人使用新角色 `customer_contact`，只赋予 `customer:confirm`；管理员在用户角色及客户工程师关联中显式关联客户。门户对该角色只认本人客户关联，不从部门扩展客户。全量范围管理员不能代替客户确认。确认只适用于工单完成、巡检成果确认，重新校验业务对象与客户归属，重复确认不覆盖第一次反馈。

客户绑定管理需要 `customer:notify`，通知中心需要 `notify:view`，补发和全局模板需要 `notify:edit`；全局模板编辑还要求全量数据范围。外网敏感写操作复用操作 MFA；正常 CSRF 保持开启。后台发送依据既有授权配置执行。

## 内容与时间口径

客户自动消息使用任务名称或“客户名称＋故障名称＋处置”主题、结构化安排和实施时间；内部描述、备注、审核原因、配置、密码、商务信息不复制到客户正文。一般服务进展须由授权人员明确确认公开；模板仅支持 `{title}`、`{content}`，不执行表达式。消息用纯文本发送，过长内容提示登录门户查看完整记录。

首次提交报告产生一次现场实施结束事件，退回及再次提交不重复产生，不修改实施结束及耗时。内部退回消息保留原因和修改要求。站内已读、接口接受、客户确认是三个不同状态。

客户通知不带免登录链接，不外发任意附件。原有报告/配置/密码的下载与 MFA 路径继续生效。内部队列文件模式明确失败为 `attachment_requires_portal`，避免后台群文件分发绕过访问边界。

## 投递策略

- 业务 Ticket、InspectionTask、Inspection 审核及 TicketProgress 的事件随 SQLAlchemy 业务事务写入；事务失败一并回滚。既有内部广播入口改为入队；关键业务的提交后通知用于完善已入队快照，不能重复创建。
- 备份失败、安全锁定和合同例外随持久化结果入队；合同到期及暂停工单提醒与幂等游标一同提交。其他遗留告警入口在调用时入队。既有站内即时通知保留；新提醒和摘要通过同一队列生成站内消息。
- 新客户绑定默认关闭。不回放启用前历史事件。旧第一期投递表保留供历史排查，不由新 worker 重放。
- 消息默认 72 小时有效；每日提醒 24 小时。最多首次尝试加 3 次自动重试，指数退避加抖动；明确 HTTP 429 尊重 `Retry-After`（最长等待一天）。未知结果不自动重发。
- 消费租约 90 秒；崩溃或发送后断连导致租约过期，记录 `worker_interrupted` 和结果未知。人工补发要求确认重复风险，并记录审计和新增尝试。
- 默认单 worker，每轮最多处理 5 个领取项，同一客户目的地最少间隔 3 秒。此为本系统保守节流参数，不代表供应商配额保证。
- 静默按北京时间整点配置，相同起止表示关闭；跨日支持。测试不受静默限制。普通业务消息静默期延后；公开进展可选 5/15/30/60 分钟窗口，最多合并 5 条同对象消息。
- 默认每天北京时间 08:30 后生成一次提醒，超时至少 3 天升级部门主管和管理员；全量范围管理员可配置时间、审核/升级天数和额外升级对象；退回及待审按照各自实际记录计算等待，不追加实施时间。个人摘要需主动订阅，周报周一；客户摘要独立默认关闭，仅计已确认服务节点。
- 每天为管理员和授权客户负责人生成失败/未知结果站内提示。worker 心跳超过 3 分钟在通知中心告警。
- 终态事件默认保留 90 天；未完成的待发、重试和发送中事件不清理。清理含尝试和投递记录，不能用数据库清空代替。

发送前重新检查绑定启用、版本、订阅、业务当前客户及接收人账号。轮换或改归属后旧队列不会自动转发到新地址。密钥轮换工具覆盖绑定凭据和内部正文；内部渠道密文配置变化会使旧目标指纹失效，应核对记录后决定重新发布，不盲目重放。

## 部署与离线更新

不增加 Redis/Celery 或 Python 依赖；使用现有 PostgreSQL、venv、systemd。迁移顺序 `c8e10f26a903 → d9a21b37f014 → eab32c480125`。SQLite 仅用于开发单次执行，持续 worker 强制 PostgreSQL。

正式发布时先提交版本并用现有 `scripts/make-release.sh` 生成同一提交的 bundle、前端 zip、SHA256 和 manifest。当前未提交工作区不是可发布 bundle，不以旧版本离线包代表本次功能。生产使用原离线上传流程和 `update.sh`；更新脚本备份后先停止旧消费者，代码、迁移、前端及 readyz 完成后安装并启动消费者。

已部署本版本且数据库迁移完成时，可由部署操作人执行：

```bash
sudo bash /home/itsm-system_20260614/scripts/install-notification-worker.sh /home/itsm-system_20260614
sudo systemctl status itsm-notifications --no-pager -l
sudo journalctl -u itsm-notifications -n 80 --no-pager
```

服务沿用 `itsm` 的 User，使用项目 `.env` 和 `venv/bin/python`。安装脚本会启用并启动发送进程，因此运行后将消费已授权的队列。离线更新不代表机器人可离线发送；运行时仍需访问对应官方 HTTPS 接口。

## 暂停与回退

```bash
sudo systemctl disable --now itsm-notifications
```

先停消费者再回退代码。新增表保留；多目的地结构禁止自动 downgrade 到第一期唯一绑定，迁移会明确拒绝破坏性回退。`rollback.sh` 已增加消费者停用，恢复后不会自动重新发送。数据库备份恢复仍是独立的数据恢复操作；先核对备份后的业务变化，不能为通知故障直接覆盖业务数据。

恢复前核对每条未知结果、待发目的地版本和有效期；按需要停用对应绑定，或在通知中心逐条处理，最后由操作人重新启用服务。已发送的群消息不保证可撤回。

## 通知文案标准（本轮业务口径修正）

巡检主题仅使用任务名称（如“景德镇市水利局2026年第三季度巡检”），不追加完成提示。故障主题使用“客户名称＋故障名称＋处置”，已包含客户名称或处置后缀时不重复添加。任务/故障名称作为可向客户展示的服务标识，内部备注应放在描述或审核字段。主题仅出现一次，正文每行一项。

巡检正文顺序为：计划时间、巡检地点、巡检工程师、任务状态、实施开始、实施结束、累计耗时、累计人天。故障对应使用故障地点、处置工程师、处置开始、处置结束。开始/执行中通知省略结束时间、累计耗时和累计人天；完成通知状态单独显示“已完成”。客户通知不写“内部审核通过”，也不保证正式报告文件已生成。内部全局通知保留审核通过；退回原因与修改要求相同时只显示一次。公开正文不带内部审核意见或附件。

“任务期限”在通知中改为“计划时间”。巡检复用任务计时函数，按现有工作时段累计、8 小时折算 1 人天，显示两位小数；并非自然时长或多人投入之和。巡检首次提交后的审核/退回等待不计入，客户现场结束通知显示“实施已结束”。故障工单只有计划到场时间，因此显示该时间，不虚构计划结束日期；处置耗时沿用工单现有计时与挂起扣除口径，本轮不修改其计时状态机。缺少可靠结束时间时不编造耗时，巡检历史人工人天保留原值。计划类消息仍按订阅发送，成果完成消息在任务完成状态产生。

客户不需要再验收。服务通知页反馈可选，兼容旧 confirm 接口和历史回执字段，不改写业务状态。存量工单状态名称与验收接口本轮不迁移；独立流程建议已按此定位修正。自定义模板删除与主题相同的独立行及重复正文行，新版本只影响新事件，旧记录不重写、不补发。
