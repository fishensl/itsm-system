# 工单/故障处置时间与敏感凭据安全整合实施方案（2026-08）

> 文档状态：实施规划，尚未按本文新增模型、接口或 UI。  
> 基线日期：2026-08-30。  
> 关联基线：`docs/implementation-plan-2026-08.md`、`docs/audit-report-2026-08.md`。  
> 范围：工单与故障处置时间统一、设备凭据传输安全、登录/MFA 会话绑定、审计、迁移、发布与回滚。  
> 不在本方案内：重新执行已完成的 G2/G3；GitHub 悬空敏感 blob 的平台垃圾回收继续按既有 G1 Support 流程处理。

## 1. 结论

本项之前没有形成完整交付物：既有安全方案覆盖密钥、MFA、权限、审计、备份和 HTTPS 门禁，也已有工单时间戳与挂起记录，但尚未定义“工单和故障到底从何时计时、何时停止、退回/挂起/重开如何计算、列表与导出显示什么”的统一口径。

本方案采用两条工作流、一个发布门禁：

1. **时间工作流**：先建立统一业务时间引擎和结构化状态事件，再补工单计时，最后让故障记录复用关联工单结果；手工故障只使用自己的明确时间边界。
2. **安全工作流**：TLS 是正式安全边界；MFA 只用于确认身份，不直接派生加密密钥。账号名、登录时间、会话和请求信息作为加密上下文和防重放绑定。已纳入实施计划的应用层双向加密信封属于纵深防御，不能替代 TLS。
3. **发布门禁**：时间字段、导出和报表不得先于数据迁移验证上线；应用层加密不得在未完成降级、跨 worker、重放和回滚测试时强制开启；敏感凭据 HTTP 兼容通道最终必须下线。

### 2.2 确定性缺口

1. `started_at` 只在接单时写入；审核退回、重开和撤回重派没有结构化计时轮次，无法准确还原多轮处置。
2. `completed_at` 在“提交审核”时写入，但故障同步以 `completed_at` 作为恢复时间；这会把“工程师提交”误当成“审核确认恢复”。
3. `service_duration` 没有统一写入和单位契约，不能作为可靠统计源。
4. 挂起时间按自然秒累计，巡检任务按工作时间计算；工单、故障、任务三套口径尚未统一。
5. 工单模型大量使用 `datetime.utcnow()`，巡检任务计时使用北京本地 naive 时间；未经数据审计直接复用会产生 8 小时偏差风险。
6. 故障记录只有“故障时间”和“恢复时间”，不能区分事件发生、接单响应、实际处置开始、审核确认和关闭。
7. 关联工单的故障记录如果允许独立修改处置时间，会形成双主数据；工单重开后历史值也可能失真。
8. 当前可信内网 HTTP 放行设备密码写入/查看时，请求或响应仍可能出现明文 JSON；可信网段只是访问边界，不等于传输加密。

## 3. 统一术语与计算口径

### 3.1 工单时间维度

| 名称 | 开始 | 结束 | 是否排除挂起 | 展示位置 |
| --- | --- | --- | --- | --- |
| 报障时间 | 用户填写的事件发生时间；缺失时回退创建时间并标记“系统估算” | — | — | 详情/导出 |
| 响应时长 | 工单创建时间 | 首次接单时间 | 否 | 详情、SLA |
| 处置时效 | 第一次进入“处理中” | 最终审核通过；无审核流程的管理关闭使用关闭时间 | 是 | 列表、详情、导出、报表 |
| 当前处理时长 | 当前处置轮次开始 | 当前时间 | 是 | 处理中实时展示 |
| 闭环时长 | 工单创建时间 | 客户验收通过或最终关闭 | 否 | 详情、管理统计 |
| 实际人天 | 处置时效的工作时间秒数 ÷ 28,800 | — | 已体现在处置时效 | 详情/导出 |

主指标“处置时效”与巡检实施时效保持同一理解：**开始处理后计时，最终审核通过后冻结**。退回修改不结束主轮次；审核等待属于该次交付闭环，但显式挂起时间不计入。为了区分工程师实际操作与审核等待，详情页同时展示状态时间线；如将来需要工时核算，应新增人工开始/暂停记录，不能从状态时效反推个人工时。

### 3.2 故障时间维度

1. **关联工单的故障**：工单是处置时间唯一真源。故障页只读展示工单的响应时长、处置时效、闭环时长和计时版本。
2. **手工故障记录**：保留 `fault_time` 为故障发生时间，新增“处置开始时间”；`recovery_time` 为恢复时间。缺少处置开始时间时可以回退故障时间，但必须显示“估算”。
3. **工单重开**：故障结果改为“待观察”，旧计时快照保留为上一轮；新一轮处理单独累计。最终展示“本轮”和“累计”，不能覆盖历史。
4. **工单删除**：有关联故障或计时事件时默认禁止硬删除；确需删除走管理员审计和软删除，保证故障档案可追溯。

### 3.3 工作日规则

- 基线工作时间：周一至周五 08:30–12:00、13:30–17:30。
- 1 人天固定为 8 小时；内部保存整数秒，前端只负责格式化，不自行计算。
- 当前先不扣除国家法定节假日；后续增加“工作日历”配置时必须带版本号，历史记录继续使用冻结时的日历版本。
- 所有新事件统一保存 UTC，API 按 Asia/Shanghai 输出；上线前必须先审计存量 naive 时间的真实语义，禁止整表直接加减 8 小时。

## 4. 目标数据模型

### 4.1 公共时间引擎

新增 `utils/business_time.py`，从 `services/task_schedule_service.py` 抽取：

- `business_seconds(start_utc, end_utc, calendar, exclusions=[])`
- `format_duration(seconds)`
- `person_days(seconds, hours_per_day=8)`
- `overlap_seconds(interval, exclusions)`

任务安排、工单和故障统一调用该模块；原任务函数保留兼容壳并加等价回归，避免一次改动破坏已上线任务统计。

### 4.2 结构化计时事件

新增 `TicketTimingEvent`：

| 字段 | 说明 |
| --- | --- |
| `ticket_id` | 工单 ID，索引 |
| `cycle_no` | 处置轮次；关闭后重开递增 |
| `event_type` | `start / submit / audit_reject / audit_approve / suspend / resume / accept / close / reopen` |
| `from_status` / `to_status` | 状态转换前后值 |
| `occurred_at_utc` | 事件时间，UTC |
| `actor_user_id` / `actor_name_snapshot` | 操作人及历史快照 |
| `source` | `ui / api / migration / system` |
| `metadata_json` | 仅非敏感原因、版本号；禁止密码、MFA、令牌 |

`TicketLog` 继续承担用户可读日志；计时计算只读结构化事件，不解析中文日志字符串。

### 4.3 冻结快照

在每轮最终审核通过或管理关闭时生成 `TicketTimingSnapshot`：

- 首次响应秒数、处置工作秒数、闭环自然秒数；
- 开始/结束、挂起工作秒数、轮次、算法版本、工作日历版本；
- `is_estimated`、`estimate_reason`；
- 生成/重算时间和操作来源。

活动工单实时计算；已完成工单读取冻结快照。历史规则调整不得静默改变已完成报表。

## 5. 状态机接线规则

| 动作 | 计时动作 |
| --- | --- |
| 接单/自己接单 | 首次进入处理中时写 `start`；同一轮重复请求幂等 |
| 挂起 | 写 `suspend`；未结束挂起区间不得重复挂起 |
| 恢复 | 写 `resume`；处置继续，主轮次不变 |
| 提交审核 | 写 `submit`，主处置时效继续等待最终审核，不冻结 |
| 审核退回 | 写 `audit_reject`，返回处理中，仍属于当前轮次 |
| 审核通过 | 写 `audit_approve`，冻结本轮处置时效 |
| 客户验收/关闭 | 写 `accept/close`，冻结闭环时长；若没有审核通过，标记“管理关闭”来源 |
| 重开 | 写 `reopen`，旧快照保留，新建下一轮 |
| 撤回重派 | 未开始时不产生处置时效；已开始后撤回应结束当前负责人片段但不丢工单轮次 |

同步修正：故障恢复时间优先取最终审核通过/验收/关闭时间，不再优先取提交审核时的 `completed_at`。

## 7. 敏感凭据安全方案

### 7.1 不采用“MFA 验证码直接加密”

MFA TOTP 通常只有 6 位，有效熵约 20 bit；截获密文后可以快速离线穷举。账号名和登录时间可预测，也不会增加密钥强度。因此：

- MFA 用于证明“当前用户确实持有第二因子”；
- 用户名、登录时间、`auth_version`、会话 ID、请求方法和路径用于绑定上下文、防止密文跨账号/跨接口重放；
- 真正的加密密钥必须来自 TLS 或高熵 ECDH 会话密钥。

### 7.2 TLS 基线：先复用现有 HTTPS 域名

内网 TLS 已决定暂缓。本批先让现有外网 HTTPS 域名完整反向代理 `/app/*`、`/api/*` 和下载接口，作为 Web Crypto 与安全 Cookie 的统一入口；内网用户也应优先使用该域名，不再以 HTTP IP 入口执行敏感操作。内部 CA、内网 DNS 与内网入口强制 TLS 保留为后续独立运维批次，不阻塞应用层信封开发。

应用层信封可让 HTTPS 代理之后到 Flask 的业务敏感字段保持密文，但不能防止代理篡改 SPA，也不替代 TLS。待内网 TLS 实施后，再开启全站 `ITSM_FORCE_HTTPS=1`、Secure Cookie、HSTS，并删除可信内网设备凭据 HTTP 例外。

### 7.3 纵深防御：会话级双向加密信封

完整协议、接口、数据模型、分批发布、测试和回滚方案见 `docs/敏感字段双向传输信封实施方案_2026-08.md`。本节只保留整合方案中的概要和依赖关系。

在 TLS 之上增加，不作为推迟 TLS 的理由：

1. MFA 成功后由后端创建短期敏感操作会话；前端用 WebCrypto 生成临时 P-256 ECDH 密钥对。
2. 后端返回一次性 challenge、服务端临时公钥、`kid`、过期时间；服务器私钥只在服务端短期保存，并由独立的 envelope wrapping key 保护，不与数据库 Fernet 主密钥混用。
3. 双方用 ECDH + HKDF-SHA256 派生 AES-256-GCM 密钥。HKDF `info` 和 GCM AAD 固定绑定：协议版本、用户名、用户 ID、`auth_version`、登录时间、会话 ID、challenge ID、HTTP 方法、API 路径。
4. 设备密码写入以密文信封提交；查看密码以密文信封返回，浏览器仅在内存中解密，不进入 Pinia、localStorage、URL、日志或错误上报。
5. challenge 60 秒失效且只能消费一次；重复、跨接口、跨账号、过期、会话版本变化全部拒绝并写安全事件。
6. MFA 码本身不进入 HKDF 密钥材料、不写 AAD、不持久化；只记录 MFA 成功时间和认证强度。

重要限制：如果 SPA 仍通过普通 HTTP 下载，主动中间人可以替换 JavaScript，在加密前读取密码，所以应用层信封只能降低被动抓包和误日志风险，不能抵御主动中间人。标准浏览器完整安全必须依赖 TLS；若必须长期无 TLS，只能使用受信任预安装客户端并固定服务端公钥，不能把 HTTP 网页包装成“端到端安全”。

### 7.4 服务端与审计边界

- 入站解密后立即做字段校验并用现有 Fernet 主密钥加密入库；事务结束前不落明文临时文件。
- `reveal-password` 继续要求 `device:reveal`、操作验证、限流、客户 scope 和审计。
- 审计只记录账号、登录时间、认证强度、challenge ID 摘要、目标设备、结果、IP/UA；不记录 OTP、密钥、明文、完整密文或 GCM nonce。
- 多 worker 环境使用 PostgreSQL/Redis 保存 challenge 使用状态；禁止进程内字典，否则跨 worker 会出现误拒绝或重复消费。
- 数据库密钥轮换、备份配对、恢复演练继续沿用已实施 G2/G3；信封只增加可轮换的短期私钥包装密钥，其丢失只作废最长 60 秒的未用 challenge，不影响数据库密文。

## 9. 迁移与历史数据

1. 先只读输出：无开始时间、完成早于开始、审核早于提交、未闭合挂起、重复故障桥接、UTC/本地疑似偏差清单。
2. 高置信度回填：`started_at`、最终通过的 `audit_at`、已闭合 `TicketSuspend` 可生成事件和快照。
3. 低置信度数据不猜测：保留原字段，`timing_source=estimated/unknown`，由管理员从审计页确认后重算。
4. `service_duration` 暂不删除；新代码停止写入，观察两个发布周期后再迁移或清理。
5. 已关联故障只绑定工单时间；多个故障指向同一工单时允许共享处置时效，但各自保留故障发生时间。
6. 回填脚本默认 dry-run，输出行数、差异和 SHA256 报告；`--apply` 前做配对备份，失败整事务回滚。

## 10. 测试与验收

### 10.1 时间计算

- 同日、跨午休、跨夜、跨周末、零时长、负时间拒绝；8 小时 = 1 人天。
- 接单开始、挂起/恢复、多次挂起、提交审核、审核退回再提交、最终通过、验收、关闭、重开第二轮。
- 活动工单实时值与冻结值；管理关闭与审核通过来源区分。
- 关联故障与工单值一致；手工故障独立计算；工单重开故障转待观察且旧轮次不丢。
- API、列表、详情、列设置、Excel 导出的字段名、值、状态颜色一致。
- 时区跨日边界测试，防止 UTC/北京时间产生 8 小时偏差。

### 10.2 安全

- 无 TLS 的敏感端点最终全部拒绝；可信网段不能绕过。
- challenge 单次使用、过期、跨用户、跨 session、跨路径、篡改 AAD/密文、GCM tag 错误全部拒绝。
- MFA 成功后才能创建敏感操作会话；密码修改、登出、管理员禁用、`auth_version` 变化立即失效。
- viewer、越 scope、无操作验证、限流触发均不能解密或查看设备密码。
- 日志、审计、异常、前端 store、本地存储和网络错误体中搜索不到明文密码、OTP 和派生密钥。
- Gunicorn 多 worker 并发消费同一 challenge 只有一次成功。

## 11. 发布、回滚与观察

1. **发布前**：当前生产只读预检、配对备份、`pg_restore --list`、迁移副本演练、前端 manifest 校验。
2. **第一批**：公共时间引擎和 schema，功能开关关闭；验证无性能回退。
3. **第二批**：管理员/测试客户灰度工单计时，抽样人工重算；误差必须为 0，估算记录单独统计。
4. **第三批**：故障联动、列表和导出；核对工单—故障一对一/多记录场景。
5. **安全批次**：先 TLS，再灰度加密信封，最后取消 HTTP 例外；不能反序执行。
6. **观察指标**：计时回填失败、负时长、未知来源、事件缺口、challenge 拒绝原因、敏感操作 403/400、登录/MFA 成功率、5xx。
7. **回滚**：先关功能开关并回退前端；新增表/列保留不删，旧字段仍可读；安全信封失败时只允许回退到已启用 TLS 的原协议，不得回退到 HTTP 明文。

## 12. 完成定义

- 工单从开始处理到最终审核通过的处置时效可准确计算，挂起、退回和重开有明确规则。
- 故障记录显示与工单一致的处置时效，手工记录不会伪装成精确工单计时。
- 列表、详情、列设置、导出和报表使用同一 metadata 与同一后端计算结果。
- 存量数据有精确/估算/未知标识，迁移可回滚且不修改无法确认的时间。
- 内网浏览器通过受信任 TLS 完成登录、MFA 和设备密码设置/查看；敏感 HTTP 兼容口已关闭。
- MFA、用户名和登录时间只承担身份与上下文绑定，不被错误当作低熵加密密钥。
- 自动化测试、全量回归、前端构建、隔离迁移演练和生产 smoke 全部通过并留档。
