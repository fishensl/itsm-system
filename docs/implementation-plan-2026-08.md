## 1. 目标与成功标准

### 1.1 总体目标

按“先止血、再可恢复、后闭环、最终收敛”的顺序完成审计整改：

1. 消除匿名敏感文件访问、存储型 XSS、任务越权、遗留明文密码导出、默认弱凭据和主密钥静默重建等风险。
2. 修复设备详情契约冲突和任务合同例外审核死胡同，使当前主流程恢复可用。
3. 建立可验证的备份、导入、发布、迁移和回滚闭环，确保失败时停止、可定位、可恢复。
4. 在产品确认后补齐备件审批、巡检转工单、SLA 提醒、满意度、销售/项目、知识库等业务闭环。
5. 逐步统一 DataTable、响应式 UI、字段元数据、权限矩阵、状态常量和 JSON Text 边界。
6. 最终收敛双轨 API、兼容壳、路由内事务和不可变发布架构。

### 1.3 建议质量指标

以下是建议默认值，正式采用前由业务负责人和运维负责人确认：

- 安全回归通过率：100%，P0 不允许已知高危例外上线。
- 全量自动化：当前 891 个 pytest 用例全部通过；Ruff、前端 lint/unit/build 全部通过。
- 备份 RPO：不高于 24 小时；关键变更前额外生成一次已验证备份。
- 恢复 RTO：隔离环境 4 小时内恢复到可登录、可解密、核心查询可用。
- 发布回滚：健康检查失败后 10 分钟内回到上一可用版本。
- 审计完整性：权限、密钥、配置、敏感导出和删除类操作覆盖率 100%。

## 2. 实施原则

1. **一个工作包一个独立 PR/提交序列**：能单独测试、发布和回滚，避免将安全、产品流程和 UI 重构混入同一批。
2. **行为变更必须带测试**：路由、权限、状态机、备份恢复和数据迁移不得只做人工验证。
3. **数据库变更只走 Alembic**：迁移幂等、先查后改；已发布迁移不可修改。
4. **路由只做边界处理**：业务规则进入 service；状态写入统一走常量和转换检查。
5. **敏感操作默认 fail closed**：权限缓存、可信网段、主密钥、备份校验和恢复配对异常时拒绝继续。
6. **不可逆操作先备份、再预演、后执行**：历史清洗、密钥轮换、历史知识正文清洗和恢复演练均遵守此顺序。
7. **兼容端点先观测后下线**：记录访问量、发布弃用告警、确认零调用后删除，除非该端点本身是高危暴露面。
8. **不在首次生产执行中验证方案**：备份恢复、密钥轮换、迁移锁和发布回滚先在隔离环境演练。

**验收**

- 不再出现固定初始管理员密码。

## 7. P1：备份恢复、发布迁移和权限边界

### WP-06 自动备份、完整性与配对轮转

**覆盖审计项**：BR-01、BR-02、BR-10、BR-11。

**任务**

1. `backup.sh` 删除 tar 吞错；必需文件缺失或归档失败返回非零。
2. PG dump 后检查非空并运行 `pg_restore --list`。
3. dump、meta、manifest 使用同一时间戳和 backup-set ID，按集合轮转；孤儿包告警隔离。
4. manifest 记录应用 SHA、Alembic head、文件清单、大小、SHA256、创建时间，不记录明文凭据。
5. 自动备份记录 last_success/last_failure/consecutive_failures；失败触发站内和外部安全告警。
6. 生产首次启用必须显式配置，系统概览展示 RPO 状态；`.secret.key*` 备份前后断言 600。

**测试与演练**

- 轮转保留完整集合，不留下孤儿 meta。
- 手工检查一个备份集合可列出 dump 内容，manifest 哈希一致。

**验收**

- 任一必需项失败，调度器能识别失败并告警。
- 系统可回答“最近一次成功备份是什么时候、包含什么、是否已校验”。

### WP-07 导入校验、staging 与原子落盘

**覆盖审计项**：BR-03、BR-04、BR-05。

**任务**

1. 将导入拆成 validate→stage→apply DB→commit→activate files/key→cleanup 六步。
2. manifest/sha256 不一致硬拒绝；旧格式必须显式选择兼容模式并记录审计。
3. 上传文件、业务附件和 secret 先解压到同文件系统临时目录，校验路径、大小、权限和可替换性。
4. pre-import 备份失败默认阻断，不再自动继续。
5. DB commit 成功后才 `os.replace` 激活密钥/文件；保留原文件回滚目录。若激活失败，进入“恢复未完成”状态并自动回滚磁盘；必要时按 pre-import 备份恢复 DB。
6. 导入期间进入维护模式，阻止并发写；成功后刷新权限缓存并执行 readiness 检查。

**测试**

- 哈希、路径穿越、超大文件、缺密钥、schema 不兼容硬拒绝。
- DB commit 失败时磁盘与密钥不变。
- 文件激活失败时原文件恢复，错误可观测。
- pre-import 备份失败时导入不开始。

**验收**

- G3 隔离演练完成：数据行数、附件、密钥解密、权限、登录、Alembic head 和核心查询正确。

### WP-08 不可变发布、健康检查和回滚

**覆盖审计项**：BR-06、BR-07、BR-08、BR-09、BR-13、BR-15。

**任务**

1. CI 为每个 commit/tag 生成不可变 release：backend SHA、frontend zip、frontend SHA256、迁移 head、依赖锁摘要。
2. `update.sh` 任一代码拉取、校验、前端 staging 失败立即退出；迁移和重启不得继续。
3. 前端部署采用版本目录+原子 symlink/rename，保留至少上一版本，不再依赖不存在的 `static/app.bak`。
4. 新增 `/healthz` 和受保护 `/readyz`；ready 检查 DB、Alembic、主密钥、前端 manifest、调度器状态。
5. `rollback.sh` 只接受完整 backup set/release manifest；缺 meta 默认拒绝。代码、前端、schema 兼容性按同一版本回退。
6. 第三方镜像下载后必须按官方 manifest 校验；镜像不作为信任根。

**测试**

**验收**

- 任一发布失败不会产生新后端+旧前端或旧后端+新前端组合。

### WP-09 迁移执行、schema 修复端点和日志

**覆盖审计项**：BR-12、BR-14、BR-17。

**任务**

1. 从 `wsgi.py` 移除每 worker 自动迁移；部署脚本在服务启动前单次执行 migration job。

**测试**

**验收**

## 12. 发布与回滚策略

### 12.1 环境推进

1. 本地/CI：完整自动化。
2. 隔离 PostgreSQL：使用近似生产 schema 的脱敏数据，验证迁移、备份和恢复。
3. 预发布：验证反向代理、可信网段、Gunicorn、多渠道通知和静态文件策略。
4. 生产：单工作包发布；P0 可以按 WP-01→02→03→05→04 代码部分推进，密钥运维窗口独立。

### 12.2 每次发布前

- 确认 PR 仅包含当前工作包。
- 记录当前 backend SHA、frontend SHA、Alembic head。
- 生成并验证备份集合；涉及文件/密钥时必须包含 meta。
- 执行全量门禁和当前工作包专项负向测试。
- 明确回滚触发条件、负责人和观察窗口。

### 12.3 每次发布后

- `/healthz`、`/readyz` 通过。
- 执行登录、设备详情、工单/任务、审计、受控下载 smoke。
- 检查错误率、403/404 异常增长、通知失败、备份状态和日志。
- 在发布记录中标记审计项为“已发布”，附 commit/release ID；不能只写“已开发”。

### 12.4 回滚触发条件

- 关键登录/设备/工单/任务流程不可用。
- 出现新的敏感数据暴露或权限扩大。
- 迁移 head、密钥、前端 manifest 不一致。
- 错误率或 5xx 显著上升且观察窗口内无法止住。
- ready 检查失败或后台调度重复运行。
